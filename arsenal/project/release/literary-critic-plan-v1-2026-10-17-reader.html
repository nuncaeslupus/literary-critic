▸Technical solution

▸Architecture overview

One .mcpb of server type uv (D-1). The app installs uv, runs uv sync against the bundled uv.lock (D-2), and starts launch.py, which starts lc mcp. The work comes in three blocks:

  1. Bundle, release, probe (T1–T3). This is the spec's first action.
    • CI packs and validates the .mcpb on every PR.
    • A version bump that is merged tags the commit, and the tag publishes the Release.
    • The owner then installs that released file on a clean PC. That one run answers desktop Q-3 and Q-8 and spec Q-5 to Q-8.
    • This replaces desktop T8, and runs desktop T1 on the real bundle (D-9).
  2. Phase 1, Option B (T4–T10). These tasks are independent of each other and can run in parallel.
    • The update check reads Releases, in the background.
    • Working state stays beside the novel, with a fallback where Controlled folder access protects the novel's folder.
    • The manuscript is changed only through Word.
    • A standalone doc-control is reported.
    • The tools declare annotations, and the setup guide says which approval answer to pick.
    • A daily workflow bumps doc-control.
    • The owner moves from the dev entry to the extension.
  3. Phase 2, self-update (T11–T13).
    • Releases carry a wheel and hashed requirements.
    • launch.py picks the newest healthy runtime, and rolls back.
    • Staging builds new runtimes in the background. The "Update automatically" checkbox controls it, and "update now" starts it at once.
    • The phase-2 release is the one manual reinstall into self-update.

The test run on a clean PC (T14, desktop T10 on the released bundle) closes the workspace by measuring every §1 criterion.

▸Technology choices

Choice Justification
Server type uv, manifest 0.4 D-1: no exe of ours, so nothing to sign; pywin32 arrives through doc-control[live]
Stdlib zipfile pack script plus npx @anthropic-ai/mcpb validate in CI Packing needs no Node; validation uses the official tool
GitHub Actions on windows-latest for the release The smoke test must import pywin32 and run uv as the app does
uv 0.9.7 in the smoke test The version the app downloads (§2)
uv export --hashes for phase-2 requirements Staging installs exactly the lock, with checked hashes
Stdlib launch.py It runs before any environment is chosen, so it can import nothing else
PowerShell Get-MpPreference, then the registry, for Controlled folder access Read-only and present on every Windows 11; which one a normal user can read is Q-8

▸Out of scope

  • Signing the .mcpb (D-12, Q-4).
  • Mac, and listing in the extension directory.
  • Blocking a standalone doc-control (D-7: reported only).
  • Moving existing working folders. A work stays where its state already is.
  • Self-updating the manifest or the launcher: those set reinstall: true.
  • Any change to doc-control itself.

▸Task details

  • T1 Pack and CI check (bundle, pack and CI check) (supersedes desktop T8):
    • extension/ holds the manifest (§5), an icon and launch.py. In phase 1, launch.py only runs lc mcp with the granted folders.
    • scripts/pack_mcpb.py zips the manifest, launch.py, pyproject.toml, uv.lock, src/ and prompts/.
    • The CI job runs uv lock --check, the pack and mcpb validate, and keeps the .mcpb as an artifact.
  • T2 Release on tag (release on tag, with smoke test):
    • Merging a version bump tags vX.Y.Z.
    • The tag runs release.yml on windows-latest. The job:
    • checks that the tag matches pyproject.toml;
    • packs and validates the bundle;
    • runs scripts/smoke_mcpb.py: unzip, uv 0.9.7 uv sync with no system Python, JSON-RPC initialize, tools/list and works, the installed versions compared with uv.lock, and the pywin32 import;
    • publishes the Release with the .mcpb, SHA256SUMS and plain notes.
    • This task ends by cutting the first release.
  • T3 Clean-PC probe (clean-PC probe on the released bundle) (desktop T1, run on the real file):
    • The PC is Windows Sandbox or a fresh account, with Controlled folder access on and no Python or uv.
    • The owner downloads the Release's .mcpb, drags it onto the app and presses Install.
    • Records:
    • each warning, word for word (desktop Q-8);
    • whether the server starts and pywin32 imports (desktop Q-3);
    • whether the server sees UV (Q-5);
    • a reinstall of the same file, to see whether the settings are kept (Q-6);
    • every approval question the app asks, and whether a group allow exists (Q-7);
    • whether a normal user can read the Controlled folder access settings (Q-8);
    • the VirusTotal result.
    • Evidence goes to status/evidence/release-probe.md, and the spec's open questions are updated.
    • If the uv type fails, stop and revise the spec (D-1).
  • T4 Update check (update check via Releases):
    • kit.update_check reads releases/latest and needs a .mcpb asset.
    • It runs in a thread started with the server, at most once a day, and writes update.json.
    • resume and works add update.
    • works(check_update=true) skips the daily limit.
    • The guide keeps install D-2's sentence rules.
  • T5 State place (working state with a Controlled folder access fallback):
    • cfa.py reads whether Controlled folder access is on and which folders it protects, from PowerShell or the registry, with a fake for tests.
    • Before the first write for a work, the place is chosen: beside the novel, or else the fallback. The choice is recorded in folders.json and returned once as state_place.
    • If the settings cannot be read, the tool tries the novel's folder once and falls back if the write is refused (winblock.kind).
  • T6 Word-only writes (manuscript only through Word):
    • When the document is closed, apply_edits asks the live engine to open it in Word, then applies the change. The file engine is never used on the manuscript.
    • Without Word, the result is a card that describes the change.
    • mcp.py sets DOC_CONTROL_STORE=appdata before doc-control is loaded.
  • T7 Other doc-control (report a standalone doc-control):
    • Read the app's extensions-installations.json (enabled entries only) and claude_desktop_config.json.
    • resume adds other_doc_control once per conversation, and the guide turns it into one sentence.
  • T8 Annotations (tool annotations and the setup sentence):
    • The annotations in §5 are added to Tool and to Tool.to_dict.
    • The guide's setup part says which answer to pick, in the words Q-7 found.
  • T9 doc-control bump (daily):
    • A scheduled workflow reads doc-control's PyPI JSON.
    • For a version inside the range, it runs uv lock --upgrade-package doc-control, bumps the patch version and opens a PR. Merging the PR releases.
    • For a version outside the range, it opens an issue.
  • T10 Owner switch (owner moves to the extension) (D-11):
    • The owner installs the released .mcpb on their own PC and removes the literary-critic-dev entry. The works are found through the shared folders.json.
    • docs/ drops the dev-entry instructions and says how a fix reaches the owner: a merge, then a release, then an update.
  • T11 Staging assets (release assets for staging):
    • release.yml also builds the wheel, uv export --hashes (with the wheel pinned by hash) and release.json.
    • reinstall is true when extension/ changed since the last release.
  • T12 Launcher (launcher with rollback):
    • launch.py reads runtime\state.json and runs the newest ready runtime.
    • It counts failed starts, which are exits within 10 s of start. After two, it marks the runtime bad and runs previous, or the bundled runtime.
    • It keeps two runtimes and is stdlib only.
  • T13 Self-update (staging, the checkbox and update now):
    • staging.py checks after the update check. It uses UV, or a uv it downloads with a pinned checksum, as Q-5 decided.
    • It builds runtime\X.Y.Z\ with --require-hashes, self-tests with initialize and tools/list, and marks the runtime ready.
    • LC_AUTO_UPDATE turns it off.
    • works(check_update=true) stages at once and returns restart_needed.
    • The first start on a new version returns update.applied once.
    • The phase-2 release sets reinstall: true, so phase-1 installs are told to reinstall once.
  • T14 Test run (test run on a clean PC) (desktop T10, run on the released bundle):
    • Install the phase-2 release from its link.
    • Run the scripted session from §1 with the novel in Documents and Controlled folder access on.
    • Then publish a patch release and restart the app once.
    • Read Windows Security's protection history.
    • The transcripts and the history give every §1 criterion.
